# TVmaze API — конспект для ShowFinder (ЛР-11)

Базова адреса: `https://api.tvmaze.com`  
Офіційна документація: <https://www.tvmaze.com/api>

## Ендпоїнти та перевірка відповідей

| Питання | Що каже документація / висновок | Запит для перевірки в Network та результат |
|---|---|---|
| Ендпоїнт пошуку за назвою, параметри | `GET /search/shows?q=:query`. Параметр `q` — назва або частина назви; пошук нечіткий, результати впорядковані за релевантністю. Пошук повертає до 10 збігів у порядку API. Значення параметра потрібно URL-кодувати. | [`https://api.tvmaze.com/search/shows?q=girls`](https://api.tvmaze.com/search/shows?q=girls) — звичайний GET; перевірити статус `200`, query `q` та `Content-Type: application/json`. Для спецсимволів: [`https://api.tvmaze.com/search/shows?q=Law%20%26%20Order`](https://api.tvmaze.com/search/shows?q=Law%20%26%20Order). |
| Форма відповіді пошуку | JSON-масив елементів `{ score, show }`. Сам об'єкт серіалу знаходиться в `item.show`; масив без збігів — `[]` із HTTP `200`, це не помилка. | [`https://api.tvmaze.com/search/shows?q=girls`](https://api.tvmaze.com/search/shows?q=girls) — масив елементів `score` + `show`. Для порожнього результату виконайте [`https://api.tvmaze.com/search/shows?q=zzzxxyyqqlab11nomatch`](https://api.tvmaze.com/search/shows?q=zzzxxyyqqlab11nomatch) та перевірте `200` і `[]`. |
| Ендпоїнт серіалу; як отримати епізоди й акторів одним запитом | `GET /shows/:id` повертає об'єкт серіалу. Документація дозволяє вкладені дані через `embed`; масивний синтаксис підтримує кілька зв'язків. Для цього застосунку потрібні епізоди й акторський склад: `embed[]=episodes` та `embed[]=cast`. Вони надходять у `_embedded.episodes` та `_embedded.cast`. Альтернатива — окремі `/shows/:id/episodes` і `/shows/:id/cast`, виконані паралельно, а не послідовно. | [`https://api.tvmaze.com/shows/82?embed%5B%5D=episodes&embed%5B%5D=cast`](https://api.tvmaze.com/shows/82?embed%5B%5D=episodes&embed%5B%5D=cast) — параметри `embed[]` розділені справжнім `&`; у відповіді очікуються `_embedded.episodes` та `_embedded.cast`. Очікувана форма: дані серіалу плюс `_embedded.episodes` і `_embedded.cast`. |
| Поля серіалу, що можуть бути `null` (із прикладом) | Не всі дані існують у кожного серіалу. Перевіряйте `summary`, `image`, `network`, `webChannel`, `runtime`, `ended`, `officialSite`, `rating.average` та поля `externals`; не звертайтеся до вкладених властивостей без перевірки. `null` — відсутнє значення, а не рядок `"null"`. | [`https://api.tvmaze.com/search/shows?q=girls`](https://api.tvmaze.com/search/shows?q=girls) містить серіал `GIRLS` з id `41734`, у якого `summary` та `rating.average` дорівнюють `null`; у його даних також трапляються nullable-властивості. Перевірити повний об'єкт: `https://api.tvmaze.com/shows/41734`. |
| Що повертає пошук без результатів | Порожній JSON-масив `[]` із HTTP `200`. У застосунку це окремий стан «Нічого не знайдено», а не мережна чи HTTP-помилка. | `https://api.tvmaze.com/search/shows?q=zzzxxyyqqlab11nomatch` — перевірити статус і тіло відповіді у вкладках Headers та Preview/Response. |
| Що повертає неіснуючий id | `GET /shows/:id` для невідомого id повертає HTTP `404`. `fetch()` сам по собі не відхиляє проміс через `404`, тому після `await fetch()` треба перевірити `response.ok` або `response.status` перед обробкою як успішних даних. | `https://api.tvmaze.com/shows/999999999` — очікується `404`; перевірити `response.ok === false`. Точний текст JSON-помилки залежить від тіла відповіді сервера. |
| Ліміт запитів і дії на `429` | Документація гарантує щонайменше 20 запитів за 10 секунд з однієї IP-адреси; за перевищення можливий `429 Too Many Requests`. Треба зачекати кілька секунд і зробити обмежену повторну спробу, а не повторювати безперервно. Для ЛР повторювати автоматично лише один раз через 2–5 секунд; наступний `429` показувати користувачу з кнопкою повтору. | У Network відкрити реальний запит до TVmaze й переглянути Status та Response Headers. Не створювати навмисно великий потік запитів: документація прямо попереджає про rate limit. Під час `429` перевірити `Retry-After`, якщо він доступний скрипту. |
| Кешування: TVmaze та браузер | TVmaze зазначає, що відповіді кешуються HTTP load balancers на 60 хвилин. Для стандартних API-відповідей використовується `Cache-Control: public, max-age=3600`. Браузер може додатково використати свій HTTP-кеш. Окремий кеш застосунку потрібен, щоб повторно відкривати вже завантажену сторінку серіалу без нового запиту; кешувати помилкові результати не можна. | `https://api.tvmaze.com/shows/1` — виконати двічі з увімкненим HTTP-кешем, потім із `{ cache: 'no-store' }`. У Network порівняти Size (наприклад, memory/disk cache) та наявність мережевого запиту. |
| CORS: документація й експеримент із preflight | Документація TVmaze стверджує, що всі API-ендпоїнти підтримують CORS; для простого GET браузер отримує `Access-Control-Allow-Origin: *`. Проте GET з несейфлістовим заголовком `Content-Type: application/json` запускає preflight `OPTIONS`. Поточне спостереження для TVmaze: такий `OPTIONS` може повернути `405` без потрібних CORS-заголовків, і тоді справжній GET не надсилається. Заголовок `Accept: application/json` дозволений у CORS safelist, тому окремого preflight для нього не потрібно. | Успішний простий запит: `https://api.tvmaze.com/shows/82`. Для перевірки preflight виконайте у Console з локальної `experiments.html`: `fetch('https://api.tvmaze.com/shows/82', { headers: { 'Content-Type': 'application/json' } })`, а потім `fetch('https://api.tvmaze.com/shows/82', { headers: { Accept: 'application/json' } })`. У Network дивіться метод і статус OPTIONS; не додавайте Content-Type до GET без потреби. |
| Ліцензія й атрибуція | Дані TVmaze ліцензовані за CC BY-SA. Потрібно вказувати TVmaze як джерело та дотримуватись ShareAlike; практичний спосіб — зберегти посилання на TVmaze у застосунку. Для ShowFinder посилання в footer не прибирати. | Джерело ліцензії: <https://www.tvmaze.com/api> та <https://creativecommons.org/licenses/by-sa/4.0/>. Перевірка проєкту: на сторінці має залишатися видима атрибуція/посилання на TVmaze. |

## Важливі технічні висновки

- `fetch()` відхиляє проміс при мережевій/CORS-помилці або скасуванні, але звичайна HTTP-відповідь `404`, `429` чи `500` сама по собі не спричиняє reject. Перевіряйте `response.ok` і `response.status`.
- Тіло `Response` — потік, який споживається один раз. Не викликайте `json()`/`text()` повторно для тієї самої відповіді.
- Для пошуку використовуйте `URLSearchParams`, щоб `&`, пробіли й інші символи не змінили структуру query string.
- Для кількох незалежних запитів обирайте `Promise.all()` (усі потрібні для результату) або `Promise.allSettled()` (потрібно окремо обробити кожен результат). Не застосовуйте `forEach(async ...)`, якщо потрібно дочекатися завершення всіх операцій.
- Скасування через `AbortController` — штатний сценарій при новому пошуку або зміні вибраного серіалу; `AbortError` не слід показувати користувачу як звичайну помилку.
- `date` і `server` можуть бути видимі в Network, але недоступні через `response.headers` для JavaScript на іншому origin, якщо сервер не надав їх через `Access-Control-Expose-Headers`.
- Для помилок UI має прибирати `aria-busy` і стан «Завантаження…»; деталі залишати в Console, а не показувати користувачу технічні повідомлення чи `alert()`.
